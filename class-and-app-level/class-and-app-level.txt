2.1 Класс слишком большой
В наших проектах большое количество классов с нарушением SRP, чаще всего встречаю Http запросы в другие сервисы с их обработкой.
Для классов с большим количеством использования думаю, что минус в том, что при изменении класса надо соблюдать его поведение
для большого количества бизнес сценариев.

2.2. Класс слишком маленький или делает слишком мало.
Чаще всего у нас это классы, содержащие отдельные Jdbc запросы, когда для остальных использовался Hibernate, для каждого запроса писался отдельный класс со своим разбором полученных данных.
Также есть классы, которые скорее всего писались AI и не были замечены разработчкиом, чаще всего это классы валидации входных параметров,
которые отвечают за валидацию тела запроса.

2.3. В классе есть метод, который выглядит более подходящим для другого класса.
Есть класс, который работает с отзывами пользователей (CRUD-операции и некоторые дополнительные) и класс, который работает с ответами продавцов.
В нашем случае при добавлении или изменении ответа мог также измениться статус самого отзыва или значение в одном из его полей. Такой метод был помещен
в класс, обрабатывающий ответы продавцов, но после "разрастания" сайд эффекта, скорее требовался перенос в класс отзывов.
Возможно даже стоило бы разделить через отбрасывание эвента во время обработки отзыва.

2.4. Класс хранит данные, которые загоняются в него в множестве разных мест в программе.
Есть получения информации о товаре, в котором также учитываются скидки и доп бонусы, из-за чего есть множество мест, в котором
меняется и дополняется объект товара в части цены и задействованных акций.

2.5. Класс зависит от деталей реализации других классов.
В MVP проекта у нас не было возможности развернуть полноценное хранилище, поэтому для хранения данных о корзине пользователя
мы сохраняли in-memory в приложении, при этом в данном случае использовалась ConcurrentHashMap, из-за чего добавление использовало
методы мапы напрямую.

2.6. Приведение типов вниз по иерархии (родительские классы приводятся к дочерним).
В проекте был абстрактный класс для обработки переводов, но один из наследников требовал дополнительных действий, которые были
помещены в метод внутри наследника. В методе, где проходились по списку, с параметризацией абстрактным классом,
приходилось проверять каждый объект на принадлежность наследнику и кастить до класса наследника, для выполнения его метода.

2.7. Когда создаётся класс-наследник для какого-то класса, приходится создавать классы-наследники и для некоторых других классов.
Было сформировано неправильное решение для классов обработки кредиитной информации. Каждый класс обработки наследовался от
своего абстрактного класса, но его дополнительное поведение было также выполнено в виде паттерна стратегия. Поэтому при
добавлении нового этапа обработки ему также соответствовал свой класс стратегии, который надо было создать.

2.8. Дочерние классы не используют методы и атрибуты родительских классов, или переопределяют родительские методы.
В проекте имелись документы для работы с API для агентов в формате txt, json и xml. Для каждого формата хранения
подразумевался класс-обработчик, который наследовался от абстрактного класса, у родительского класса при этом уже был свой
метод, который содержал пайплайн обработки, а переопределяться должны были методы, которые этот пайплайн вызывал,
но в какой-то момент обнаружилось, что для нового типа документов пайплайн должен быть изменен на несколько шагов,
в результате чего класс начал переопределять и родительский метод с пайплайном.

3.1. Одна модификация требует внесения изменений в несколько классов.
В сервисе есть несколько ручек, которые отдают информацию для отображения на различных экранах по поводу товаров, на каждом экране
есть признак "возможно вернуть в один клик", такое условие изначально рассчитывалось сразу при маппинге, из-за чего при создании других мапперов
функция просто копировалась. Теперь для изменения этих условий нажо менять одинаковые функции в нескольких классах.

3.2. Использование сложных паттернов проектирования там, где можно использовать более простой и незамысловатый дизайн.
В проекте был паттерн, в котором после окончания транзакции откидывалось специальное spring-событие, и обработчик, который был внутри того же сервиса,
прослушивал его и выполнял http запрос с последующей обработкой, цель была в том, чтобы отправлять событие только после завершения транзакции.
Мне кажется это могло бы быть заменено обычным аутбокс паттерном.

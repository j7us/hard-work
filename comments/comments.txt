В данном проекте были взяты примеры из все того же сервиса возврата товаров, количество кода было сокращено или срезано
до использования интерфейсов. Для примера были выбраны классы с неочевидной или переиспользуемой бизнес-логикой:

1-й пример:

/**
 * Сервис проверяет доступность отдельных товаров в заказе и их доступность для возврата.
 * Переиспользуется в нескольких пользовательских флоу для дополнительной проверки товара перед созданием заявки.
 * Требования к досутпности описаны также в Confluence
 */
@Component
@RequiredArgsConstructor
public class OrderItemAvailableStatusResolver {
    private final ReturnRepository returnRepository;

    public String getOrderItemStatus(OrderItem orderItem) {
        if (orderItem.getReturnable()) {
            return "NOT_AVAILABLE";
        }

        List<Return> returns = returnRepository.getAllByOrderItemId(orderItem.getId());

        if (!CollectionUtils.isEmpty(returns)) {
            return "NOT_AVAILABLE";
        }

        return "AVAILABLE";
    }
}

Здесь класс для дополнительной проверки, который переиспользуется на каждом этапе при проверке товара на возможность его оплаты.
Я посчитал нужным указать в комментарии, что необходимо обращать внимание, что внесенное изменение будет отображаться на проверки на каждом
этапе возврата товара, поэтому лучше не вносить туда специфичные для какого-то отдельного момента проверки.

В данном проекте tdd реализован через unit тесты, как было описано в курсе карьеры, тесты покрывают два класса, один для самого
сервиса продуктов и второй для класса расчета статусов (код представляет собой небольшой пример показа статусов заказанных товаров).
Я уже пытался использовать tdd для этого, но сейчас сильно помогла мысль о том, что unit-тесты являются некой спецификацией,
которая описывает наш код. Также после прочтения "Три уровня рассуждений о программной системе" я лучше понял мышление на разных уровнях,
но не совсем еще понял фразу "Код не должен следовать тестам, ни тесты не должны следовать коду", для себя на данный момент
определил это как то, что unit тест должен проверять наименьшие части программы, но пишем мы unit тест именно с точки зрения 3 уровня,
без мысли о внутренней реализации метода. Например мой тест подает в метод какой-то входной параметр и независимо от реализации кода
мы ожидаем именно определенный статус для возвращения

@Test
    void calculateStatushalsOrderTest() {
        String resultStatus = productStatusCalculator.calculateCurrentStatus(
                new Product(UUID.randomUUID(), "a", LocalDateTime.now().minusDays(5), false, 5, 3)
        );

        assertThat(resultStatus).isEqualTo("HALF_ORDERED");
    }

Также в моей логике и дальнейшем устройстве бд подразумевается например, что product.orderedAmount будет всегда заполнен
при создании продукта, а product.amount будет по дефолту проставляться как 0, поэтому не требуется добавлять дополнительные
тесты на проверки, которые не подразумевает логика приложения, думаю это и относится к фразе
 "И тесты, и код должны следовать дизайну, логической архитектуре"
